1. Introducción

ATALAYA es un sistema de asistencia a la operación de una central nuclear: recibe señales de planta, estima la probabilidad de distintas desviaciones y genera alertas para la sala de control. No tiene ningún camino de escritura hacia los sistemas de control ni de protección, así que el riesgo que nos importa es que el operador tome una mala decisión por una alerta falsa, una alerta que no llega o que llega tarde, o por exceso de alertas.

El enunciado no trae código y los lineamientos piden entregar el SISTEMA en Java 21 con Spring Boot. Por eso implementamos una versión reducida de ATALAYA que cubre la lógica de mayor riesgo y, sobre ella, planificamos, diseñamos y ejecutamos las pruebas. Como confirmó el profesor, la complejidad del código no es el objetivo: lo mantuvimos chico para que las pruebas sean lo importante.

2. Sistema bajo prueba y alcance

El SISTEMA es una API REST con Spring Boot, persistencia en H2 y autenticación por roles con Spring Security, más un panel web mínimo para la sala de control. Las estimaciones del modelo de IA no se calculan: en el perfil qa se inyectan por un endpoint, igual que el avance del reloj, que es un java.time.Clock inyectado en las clases que manejan tiempos. Así podemos probar 45 s o 3 min sin esperar.

3. Fundamentos aplicados

Verificamos con revisión de requerimientos, revisión de código y pruebas contra cada RF. Validamos con criterios de aceptación escritos para que operación y seguridad puedan leerlos (sección 9). En el informe usamos error para la equivocación de una persona, defecto para lo que queda mal en un artefacto y falla para lo que se observa al ejecutar. Por ejemplo: interpretar “más del 2 %” como “2 % o más” es un error; escribir >= en vez de > en el validador es el defecto; que un canal al 2,00 % quede como no confiable es la falla (CP-08).

6. Plan de pruebas

El objetivo es reunir evidencia suficiente sobre la lógica de mayor riesgo para poder recomendar si se libera o no. Probamos lo incluido en la sección 2. La estrategia es basada en riesgos: primero redundancia, niveles y escalamiento, después maniobras, configuración y la interfaz.

No probamos lo que quedó fuera del alcance en la sección 2, ni el modelo de IA. Sobre el modelo, el requerimiento pide una sensibilidad mínima del 95 %, y con pocos eventos críticos ese número es engañoso: 19 detecciones sobre 20 dan 95 %, pero el intervalo de confianza va aproximadamente de 75 % a 99,9 %. Para afirmar que la sensibilidad es de al menos 95 % con 95 % de confianza harían falta unos 59 eventos detectados sin ninguna falla. Lo dejamos planteado como método para cuando el modelo esté disponible.

Para empezar a ejecutar pedimos que el proyecto compile con mvn verify, que exista el perfil qa y que los casos estén revisados por otro integrante. Para terminar, que todos los casos estén ejecutados, que no haya defectos críticos abiertos y que la cobertura y la mutación superen lo definido en la sección 11. Suspendemos si el build falla o si un defecto bloquea el resto de las pruebas, y retomamos repitiendo los casos afectados.

7. Diseño de pruebas

Probamos en cinco niveles. Unitario: las clases de dominio con JUnit 5, y los servicios aislados con Mockito. Integración: los servicios con H2, usando Spring Boot Test. Sistema: la API con MockMvc, contra el servidor real y con Postman. Interfaz: el panel con Selenium. Aceptación: escenarios en Cucumber. Las técnicas de caja negra se aplican donde hay reglas con bordes claros, la caja gris donde importa lo que queda guardado en la base, y la caja blanca en las dos clases con más decisiones. No hacemos combinatoria completa (serían 162 casos) ni esperas en tiempo real, que son lentas y frágiles.

7.3 Caja blanca

Para ClasificadorNivel tomamos el código y calculamos la complejidad ciclomática: cuatro decisiones, V(G) = 5. Elegimos un dato por cada camino básico y agregamos p = 100,1 para cubrir la segunda condición de D1 (CP-17). Con ServicioEscalamiento hicimos lo mismo apuntando a cobertura de decisiones (CP-26). Las dos clases quedaron con 100 % de sentencias y ramas en JaCoCo.

public NivelRiesgo clasificar(BigDecimal p, Umbrales u) {
    Objects.requireNonNull(p, "La probabilidad es obligatoria");
    if (p.compareTo(minimo) < 0 || p.compareTo(maximo) > 0) {   // D1
        throw new ProbabilidadInvalidaException(p);
    }
    if (p.compareTo(u.critico()) >= 0) {                         // D2
        return NivelRiesgo.CRITICO;
    }
    if (p.compareTo(u.alto()) >= 0) {                            // D3
        return NivelRiesgo.ALTO;
    }
    if (p.compareTo(inicioAtencion) >= 0) {                      // D4
        return NivelRiesgo.ATENCION;
    }
    return NivelRiesgo.NORMAL;
}

minimo, maximo e inicioAtencion son 0, 100 y 15. Están como campos de instancia y no como constantes static final para que PIT pueda mutarlos (sección 10.2).

10. Automatización, TDD, API e interfaz

Automatizamos todo lo que tiene un resultado verificable sin juicio humano: reglas de dominio, servicios, API e interfaz. Usamos JUnit 5 con pruebas parametrizadas, Spring Boot Test y MockMvc, Cucumber para los criterios de aceptación, Selenium para el panel, JaCoCo para la cobertura y PIT para la mutación. Todo corre con mvn verify en un clon limpio, y cada clase de prueba tiene un comentario con su propósito y el ID de los casos que cubre. Cada test lleva el ID en el nombre que muestra JUnit (CP-xx, UI-xx, o INF-xx para las dos pruebas del reloj y de los endpoints de QA, que prueban la infraestructura de pruebas y no el SISTEMA).

El Makefile tiene un comando por tipo de prueba (make test-unit, test-api, test-integration, test-bdd, test-ui), uno para mutación (make mutation) y uno que corre todo y guarda la salida como evidencia (make evidence). Con OPEN=1 cualquiera de ellos abre al terminar un reporte HTML con los totales, los casos por tipo, los IDs del catálogo ejecutados, la cobertura y el mutation score.

10.1 TDD

Aplicamos TDD en ValidadorRedundancia y ServicioEscalamiento, que son reglas precisas con bordes numéricos y de tiempo. Hicimos tres ciclos en cada clase: primero el test que falla, después el mínimo código para que pase. La salida de cada ejecución en rojo y en verde está en docs/evidencias/tdd/ (doce archivos). No dejamos un commit por etapa, como decía la versión anterior de este informe: la evidencia del ciclo es esa salida.

10.2 API y Postman

La colección de Postman tiene una carpeta por requerimiento, un entorno con baseUrl y usuarios por rol, y scripts que verifican código HTTP y cuerpo de la respuesta. Cada request que lo necesita llama antes a /qa/reset. La corremos completa con newman (make test-postman), que levanta el SISTEMA si no está arriba: 97 requests, 156 aserciones, 0 fallos. La salida queda en docs/evidencias/postman/.

Las mismas reglas de la API también se prueban con MockMvc. Postman encontró algo que MockMvc no veía: sin credenciales, el servidor real respondía 302 al login en vez de 401 (ATA-16). MockMvc no hace el reenvío interno a /error que causaba el problema. Desde entonces hay pruebas contra el servidor real (SeguridadServidorRealTest).

10.3 Interfaz con Selenium

El panel se prueba con Selenium usando Page Objects (página de login y página del panel). Los elementos que usan las pruebas tienen un atributo data-test, y las esperas son por condición, nunca fijas. En mvn verify corre con HtmlUnit, sin navegador; con make test-ui-chrome corre en Chrome, y make test-ui-demo deja el navegador abierto al final de cada prueba para la exposición. Las capturas de la ejecución en Chrome están en docs/evidencias/selenium/. Al revisarlas apareció un defecto que las pruebas no detectaban: los estados de los tres canales salían pegados en un renglón (ATA-18). Agregamos el test que lo muestra, lo vimos fallar y después lo corregimos.

10.4 Mocks

La mayoría de las pruebas usan el SISTEMA real con H2 y el reloj de prueba, sin mocks. Usamos Mockito en dos lugares donde un mock aporta algo que la prueba real no da. En ServicioUmbralesTest el repositorio y el validador son mocks, para comprobar que, cuando una regla corta, el servicio no guarda ni cambia nada (CP-32, CP-33, CP-40). En ConflictoConcurrenteApiTest el servicio de alertas es un mock que lanza el choque de versión de JPA: así el 409 de CP-25 se prueba sin depender de que dos hilos se crucen.

10.5 Mutation testing con PIT

PIT se corre sobre el paquete de dominio con los mutadores por defecto más INLINE_CONSTS. Los mutadores por defecto no cambian constantes; sin INLINE_CONSTS no aparecen mutantes como “45 s pasa a 46 s”. Por la misma razón, los límites están como literales o campos de instancia: PIT no muta los inicializadores static final. Nos interesan sobre todo los mutantes que cambian bordes, porque son los defectos más probables en este SISTEMA:

11. Defectos, Definition of Done y métricas

No tuvimos Jira. Los defectos se registran en docs/defectos.md y en la hoja Defectos de la planilla, con versión, caso, pasos, resultado esperado y observado, evidencia, severidad y prioridad. La severidad es crítica si puede llevar al operador a una mala decisión, alta si demora o duplica una alerta, media si es un error sin efecto directo y baja si es cosmético. El flujo es Nuevo, Confirmado, En corrección, Corregido, Verificado y Cerrado. Si una prueba sigue fallando al entregar, es porque evidencia un defecto registrado, y lo indicamos en su nombre. Los defectos corregidos también quedan citados en el nombre del test que los evita (por ejemplo, “[defecto ATA-16, corregido]”).

Lo más importante que encontramos no estuvo en el código sino en el enunciado: doce puntos donde el requerimiento admite más de una lectura, cuatro de ellos con severidad alta (ATA-1, ATA-3, ATA-5, ATA-8). Los tres defectos del SISTEMA se encontraron con pruebas distintas de las que los “tenían” que encontrar: el 302 apareció con Postman y no con MockMvc, la base compartida apareció como un test que fallaba a veces, y el problema del panel apareció mirando las capturas, no en las aserciones. Eso confirma que conviene combinar niveles y herramientas.

Riesgos residuales:

  • El comportamiento del modelo real, que no pudimos probar.
  • Los requerimientos que quedaron fuera del alcance (RF-04/05, RF-10, RF-11).
  • Las ambigüedades de la sección 5 que la cátedra no llegue a aclarar: si la respuesta difiere de nuestra decisión, cambian los casos que la verifican.
  • La concurrencia se probó con dos usuarios a la vez (CP-25), no con carga real.

Limitaciones:

  • El SISTEMA es una implementación reducida hecha por nosotros, no el ATALAYA real.
  • Los datos son sintéticos.
  • El mismo equipo desarrolla y prueba, lo que resta independencia.

Recomendación de liberación: recomendamos liberar la versión 3.1.0 para el alcance probado. Se cumplen todos los criterios de salida de la sección 11 y no queda ningún defecto del SISTEMA abierto. La condición es que la cátedra confirme las decisiones de severidad alta (ATA-1, ATA-3, ATA-5 y ATA-8), porque cambian qué canal se usa, cuándo se repite una alerta y cuándo deja de agruparse una maniobra.

Como mejora queda probar los requerimientos excluidos, sumar pruebas de carga para la concurrencia y evaluar el modelo real con datos de transitorios y arranques.
